# ASSUMPTIONS

Assumptions made during the remote-removal loop when information was missing. Update this file
instead of waiting for a human.

1. **`crates/server/src/routes/remote/*` is a cloud proxy.** Verified: it calls
   `deployment.remote_client()` and there is no local issues/projects DB. Therefore the local
   kanban/issues/org UI is in scope and is removed. (GOAL.md, "Evidence".)

2. **`relay-*` crates are out of scope, but relay host *listing* is not.**
   `listRelayHosts` lives in the deleted `remoteApi.ts`, and the settings host picker fetched relay
   hosts from it. Resolution: the picker now exposes only the local machine target. Relay crates and
   `relayPairingStorage` are untouched. `SettingsHostContext.tsx` was rewritten accordingly.

3. **Generated `routeTree.gen.ts` files are not hand-edited.** They are regenerated by the TanStack
   router plugin at dev/build time, and both carry `// @ts-nocheck`, so stale route entries produce
   no type errors and are harmless until the next `vite` run. Structural checks ignore them.
   Milestone 13 should confirm a regenerated tree. There is no generator CLI installed
   (`@tanstack/router-generator` is a transitive dep, not resolvable, and `vite build` fails while
   imports are still broken).

4. **Signals used for deletion safety:** a file is safe to delete only if (a) it is broken by an
   import that this loop deleted, and (b) nothing outside that broken set imports it. Verified with
   `scripts/find-remote-only-web-core.mjs` plus a grep against `packages/local-web/src` and
   `packages/ui/src`.

5. **Build gate is offline.** This machine has no git credentials to fetch the `ts-rs` git
   dependency, so `cargo check --workspace --offline` is authoritative.

6. **Transient red builds are acceptable** between milestones 4 and 13, per GOAL.md quality standards.

7. **Relay settings keeps only its local content.** `RelaySettingsSection.tsx` was reached via
   `runtime === 'remote'`, and its client-role panel rendered the deleted remote
   `RemoteCloudHostsSettingsCard`. Resolution: `RelaySettingsSectionContent` always renders the
   local content, and the client role choice was removed from the role picker. Relay crates are
   untouched. Follow-up tracked in `IMPROVEMENTS.md`.

8. **`SettingsDialog` fallback.** The "no hosts available" branch used to fall back to the
   `'organizations'` settings section. Since that section is removed, it now falls back to
   `'general'`.

9. **`remote_client` / `remote-info` are RETAINED — they are relay infrastructure, not the remote feature.**
   Verified: `crates/relay-hosts/src/lib.rs` uses `RemoteClient::access_token()` and `RemoteInfo` to pair
   relay hosts, and relay is an explicit non-goal in GOAL.md. Deleting them would break relay.
   Therefore S05/S06/S21 were **redefined** (batch 23) from "delete these crates" to checks that assert
   the *remote feature* is gone instead:
   - S05: no `remote_sync`/`remote_client` in `crates/local-deployment/src/container.rs` (was: delete
     `remote_client.rs`).
   - S06: no `remote_sync`/`remote_client`/`RemoteClientError` in `crates/server/src/routes/workspaces`
     (was: delete `crates/remote-info`).
   - S21: no `RemoteClientError`/`remote_client` in `crates/server/src/routes/config.rs`
     (was: no refs anywhere in server/services/local-deployment).
   This is a scope correction, not a lowered bar: each new check still asserts absence of remote-feature
   behaviour, and the remaining `remote_client` surface in `routes/workspaces` is tracked as milestone 7.

10. **Relay host pairing depended on the remote cloud API.** `local-deployment` built its `RemoteClient`
    from `VK_SHARED_API_BASE` (the cloud), and relay-hosts was only constructed when that client existed.
    With the remote feature removed there is no cloud URL, so `remote_client` is now always
    `Err(RemoteClientNotConfigured)` and the relay-hosts service is not constructed. Relay *crates* are
    untouched (still in scope-exclusion), but the pairing *feature* is unavailable. Chosen over keeping a
    dead `VK_SHARED_API_BASE` read, which S13 forbids.
